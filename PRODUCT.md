# NeuralLab product

NeuralLab is a local-first deep-learning fieldbook: learners manipulate real numbers, predict a result, inspect an executable calculation, explain it, and return for retrieval practice. The interface should make mathematical relationships visible without equating a visit, a correct answer, or a scheduled review with mastery.

## Learners and journeys

Absolute beginners use the 60 authored topics in chapters 00–07. Students revisiting course material explore the 12 available experiment labs. Learners who want to write code use the editable Python workshop; those integrating concepts train and inspect a small regression model. The research library contains 19 chapters and 149 lesson specifications; advanced specifications are not implemented courses.

Primary journeys:

1. Start beginner course → make a numerical prediction → execute Python → inspect operations → answer an explanation check → attempt the transfer case.
2. Open a lab → adjust its parameters → inspect the computation → test a prediction. The neuron field challenge asks for a bias producing ReLU output 1.5 and restores the previous parameter configuration when finished.
3. My learning → recommended next topic or due recall → review → inspect the chapter map. Its labels derive from existing evidence, not points or a new score.
4. Edit Python or train a model → predict → execute → inspect results and errors. Checkpoints preserve inference weights, not full optimizer-state resume.

## Principles and priorities

Keep the existing engines, lesson catalog, Python authority, hint provenance, FSRS scheduling, portable backups, and accessible 2D alternatives. Exploration stays open; chapter-map ordering suggests a path without locking topics. Sandbox experiments do not earn authored-course evidence.

This iteration improves orientation, navigation history, shared surfaces, inspectable 2D nodes, and a small authentic challenge. It does not add arbitrary drag interactions, rewards, paid services, advanced lessons, or claims of retained mastery. Preserve the supplied teal/slate identity.

Future priorities: address individual topics in URLs; fresh validated transfer items; chapter-specific mission checkpoints; teaching divergence rather than only rejecting it; independent learner evaluation. These need separate changes and evidence.

## Success measures and constraints

Engineering measures: existing journeys still execute, URL reload and Back/Forward preserve the intended workspace, keyboard users can open/close the drawer, controlled computations agree with tested engines, and representative viewports have no horizontal overflow. Evidence is in [the delivery report](docs/engineering/WORKSPACE_RENAISSANCE.md).

Learning measures to evaluate with learners: explanation quality, unaided transfer performance, and delayed recall. No such study was conducted. The 90% interaction philosophy guides task selection; it is not a measured ratio or outcome.

Zero-budget operation, no required account, browser-local storage with export/restore, mobile CPU/GPU limits, and a pinned network-loaded Python runtime constrain the design. Clearing storage loses unexported evidence. Python editing restrictions are learning controls, not a server security boundary.
